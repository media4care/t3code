# Workflow insights

Open **Insights** in the sidebar or command palette to review how your agents work. On mobile, use the Insights tab; it may be under More if you have customized your tabs. Choose the environment whose threads you want to analyze.

In Insights settings, choose a project for the analyst to work from, an available Codex Astra model, the projects to review, and a daily time. The review runs at max reasoning effort. **Model for applying changes** picks the model for the threads that apply a recommendation; left alone, they use the analysis model at its default effort. Times use the server's local timezone, and the server must be running. Pause or resume the schedule anytime, or use **Refresh insights** to run a review immediately and display its results, including while the daily schedule is paused. Analyses consume your provider's normal usage allowance. **Reload saved reports** on web and desktop, or pull to refresh on mobile, reloads saved reports without starting an analysis.

The first analysis reviews recent activity within your chosen lookback window. Later analyses review new or changed work. Large backlogs carry over to subsequent analyses. The dashboard opens with a **Decision brief**: a headline and up to three things to decide or change. Each one is marked as coaching on how you brief and steer agents, or as a change to your toolkit, with the threads it comes from; a toolkit change opens its recommendation. The dashboard also summarizes activity and recommended changes. **Tasks sampled** lists each task the review sampled (a thread together with its subagent threads), with its project, run count, follow-ups you wrote, interrupts, questions the agent asked through its question and approval tools, failed tools, pull request state, and how many findings cite it; select one to open it. Messages an agent sent into a thread do not count as your follow-ups. A citation shows where a finding came from, not how important the task is. Reports from before task measures list threads instead. **Recurring friction** groups tool failures by program, exit code, and error, and lists the ones that came back across tasks or within one task, with a link to an example and the recommendation that addresses it, if any. A search that found nothing and failures that printed no error are left out. Expand **Analysis & evidence** for the full report, coverage, missing data, and links to source threads. A completed run does not prove a task succeeded, and missing token usage is not treated as zero usage. **Skills used** counts the reviewed runs that loaded each skill. Only Claude and OpenCode report skill loads, so skills used by other providers are missing.

A recommendation says what happened, what the change makes agents do differently, and how later work would show that it helped. **Proposed change** shows the exact edit: the file, the lines it removes, and the lines it adds. The analyst checks the edit against the file before saving it. Recommendations from before exact edits describe the change in words instead. A recommendation keeps the wording it was first written with; when a later review sees the same problem again, it adds an entry under **Came back** with the threads involved.

**Open a PR with this change** starts an agent thread that applies the edit in its own worktree and opens a pull request for you to review. A file in a git submodule gets its pull request in the submodule's repository. Where a pull request is not possible, such as a project without a remote or a file outside your projects, the thread makes the change in place and leaves it uncommitted. For a recommendation without an exact edit, **Have an agent make this change** starts a thread that works out the edit first. You can also accept, defer, dismiss, or reopen each recommendation, with a decision note.

The **Implementation** view shows which recommendations are not implemented, started, or implemented. These states reflect recorded decisions: starting a thread does not confirm completion. Add a commit, PR URL, or other change reference and choose **Mark implemented** once the change is merged. That starts a trial: later reviews assess it against **How we'll know it worked**, using only work done after the change, as improved, unchanged, regressed, or not yet clear. The decision brief may ask you to settle it. The trial keeps that criterion as it was when you started it, so a later review cannot move the goalposts, and each run counts once. Choose **Keep** when the criterion is met, **Revise** to send it back for more work, or **Mark reverted** after you have undone the change yourself. Kept and reverted recommendations are no longer assessed. **Reopen trial** resumes assessing a kept change; reopening a reverted one starts over.

The daily analyst reads thread excerpts and relevant workspace files through your selected provider. It proposes changes without applying them. Reports stay in that environment, so connect to the same server from another client to see the same recommendations and decisions.

To cover several machines in one report, turn on **Linked environments** in Settings → Labs on each of them, and link the other machines from the one that runs Insights. Its Insights settings then list **Projects on** each linked machine; you must be connected to that machine in the app to choose them. A linked machine must be running when the analysis runs. If it can't be reached, the report says so and picks up its activity next time. A thread that applies a change works in a checkout on the machine that runs Insights.
